# ТЗ: OSM Flight Sim (рабочее название `sim-unlimited`)

> Статус: **v1.0, согласовано** 2026-11-08. Открытых пунктов нет; все решения (Q1–Q46) сведены в таблицу §12. Изменения после v1.0 — только через новую запись в §12.

## 1. Цель и рамка

Браузерный авиасимулятор, в котором мир — это реальная Земля, собранная на лету из данных OpenStreetMap и карты высот. Мир сквозной: можно взлететь в любой точке и лететь куда угодно без загрузочных экранов, тайлы подгружаются и выгружаются по мере полёта.

Визуальный язык — ранние 90-е: F-117A Nighthawk Stealth Fighter 2.0 (MicroProse), Su-27 Flanker (SSI). Плоская заливка полигонов без текстур, ступенчатое освещение, дальний туман полосами, векторный HUD. **[РЕШЕНО, Q43]** Цвета любые (полноцветный RGB, без привязки к VGA-палитре); текстуры по-прежнему запрещены. При этом рендер в **нативном разрешении** экрана (без пикселизации, с учётом `devicePixelRatio`) — ретро-стиль достигается плоской заливкой, ступенями света и тумана и геометрией, а не низким разрешением или бедной палитрой.

### 1.1. Не цели (для MVP)
- Фотореализм, текстуры (любые, включая процедурные и спутниковые подложки), PBR, тени в реальном времени.
- Боевая часть, ИИ-противники, миссии. **[РЕШЕНО, Q1]** MVP — песочница (свободный полёт, взлёт/посадка где угодно); архитектура сущностей закладывается так, чтобы бой добавить позже без переделки.
- Мультиплеер.
- Сертифицируемая физика полёта.
- Мобильные устройства (только десктоп-браузер с WebGL2).

## 3. Система координат и сквозной мир

- **Тайловая сетка**: Web Mercator (slippy map, z/x/y), единая для рельефа и OSM-данных. Базовый уровень для зданий и дорог — z14 (~2.4 км по стороне на экваторе, ~1.4 км на широте Москвы).
- **Мировые координаты**: double-точность хранится на CPU (широта/долгота или ECEF); на GPU уходят float32 координаты **относительно плавающего начала (floating origin)**. При удалении самолёта от начала более чем на N км (предложено 5 км) происходит ребазирование: все загруженные чанки получают новый offset uniform'ом, без пересборки буферов.
- **Локальная плоскость**: каждый чанк строится в своей локальной ENU-системе (East-North-Up) от центра тайла, в метрах. Масштабные искажения Меркатора компенсируются при построении (переводим lat/lon → метры через ENU, а не через пиксели Меркатора).
- **Кривизна Земли** **[РЕШЕНО, Q12]**: мир плоский в пределах чанка; глобальная кривизна имитируется в вершинном шейдере опусканием на `d²/2R` от камеры. Даёт правильный горизонт на высоте без перехода на полноценный глобус.
- **Полюса**: Меркатор не покрывает >85°. Для MVP полёт ограничен ±85° широты.

## 4. Рельеф

### 4.1. Источник
**[РЕШЕНО, Q12]** AWS Terrain Tiles (формат Terrarium, PNG, `elevation = R*256 + G + B/256 − 32768`), публичный бакет с CORS, z0–z15. Альтернативы: Mapbox Terrain-RGB (нужен ключ), MapTiler (ключ), Copernicus GLO-30 через свой сервер.

### 4.2. Меш
- Квадродерево чанков (chunked LOD): уровень детализации зависит от расстояния до камеры и высоты полёта. Ближние чанки z13–z14, горизонт z8–z9.
- Сетка на чанк — регулярная, например 64×64 квадов; в ретро-стиле треугольники **намеренно крупные** и видимы как грани.
- Швы между уровнями: «юбки» (skirts) по краям чанка. Морфинг между LOD — опционально (в стиле эпохи допустим поп-ин, но лучше без мелькания).
- Освещение: flat shading (нормаль на грань), направленный «солнечный» свет, яркость квантуется в ступени (см. §7).
- Окраска граней по высоте/уклону/landuse: вода, пляж, трава, лес, скалы, снег.
- Вода (океан): плоскость на 0 м под рельефом + полигоны `natural=water` из OSM.
- **[РЕШЕНО, Q13]** Граница суша/море — маска по DEM: `h ≤ 0` → вода. Известное и принятое ограничение: прибрежные низины ниже уровня моря (польдеры, дельты) затапливаются. Береговые water polygons OSM не используются.

### 4.3. Привязка объектов к рельефу
- Здание ставится на **минимальную** высоту рельефа под его контуром (фундамент уходит в склон, без висящих зданий).
- Дороги и полигоны землепользования «драпируются»: точки сэмплируются из той же карты высот, что и меш, плюс небольшой bias по глубине против z-fighting.
- ВПП выравниваются: рельеф под `aeroway=runway` сглаживается до плоскости (иначе взлёт невозможен на шумном DEM).
- **[РЕШЕНО, Q40]** Порядок загрузки: старт ждёт, пока в точке старта загрузятся и рельеф, и OSM (экран загрузки). Без данных не стартуем: если OSM недоступен — экран ожидания с повтором, без фолбэка. В полёте чанк рельефа сначала строится «как есть», а когда приходят данные OSM, ближние чанки z12–z14 перестраиваются в воркере с выровненными ВПП (короткий поп-ин допустим).

## 5. Данные OpenStreetMap

### 5.1. Источник для MVP **[РЕШЕНО, Q2]**
MVP — чисто статический фронт: прямые запросы к Overpass + кеш в IndexedDB. Все источники скрыты за интерфейсом `TileSource` (`fetch(z,x,y,lod) → нормализованные фичи`), чтобы позже подключить свои векторные тайлы (PMTiles) или прокси без изменений в генераторе мешей.

- **[РЕШЕНО, Q42]** Прямой запрос из браузера невозможен: главный инстанс Overpass отдаёт 406 браузерным User-Agent, а `fetch` не позволяет переопределить UA. В dev-режиме запросы идут через same-origin прокси Vite (`/overpass`), который подставляет описательный UA. Статический прод-билд до M6 к Overpass обращаться не может — публичный путь только через свои тайлы (Q9, M6).

- **Overpass API** с фильтрами по bbox тайла z14. Политика использования главного инстанса: порядка 10 000 запросов/сутки и ~1 ГБ трафика на пользователя; для пет-проекта/демо подходит, для публичного запуска — нет.
- **OSM API 0.6 `/map`** — не подходит как основной источник: лимит 0.25°² и 50 000 нод, политика запрещает массовую загрузку для рендера. Допустим как отладочный fallback.
- **[РЕШЕНО, Q9]** Проект будет публичной демкой, а публичный Overpass её трафик не выдержит и политика это запрещает. Поэтому перед публичным запуском обязателен этап M6: свои векторные тайлы (собственная генерация из planet/extract через tilemaker/planetiler в формате MVT/PMTiles).

### 5.2. Запрос Overpass (черновик)
```
[out:json][timeout:25][bbox:{s},{w},{n},{e}];
(
  way["building"]; relation["building"]["type"="multipolygon"];
  way["building:part"]; relation["building:part"]["type"="multipolygon"];
  relation["type"="building"];
  way["highway"~"motorway|trunk|primary|secondary|tertiary|residential|unclassified"];
  way["railway"="rail"];
  way["aeroway"~"runway|taxiway|apron|helipad"]; node["aeroway"="helipad"];
  way["natural"~"water|wood|scrub|beach|bare_rock"]; relation["natural"="water"];
  way["waterway"~"river|riverbank|canal"];
  way["landuse"]; relation["landuse"];
  way["leisure"~"park|pitch|golf_course"];
  way["man_made"~"bridge|tower|chimney|mast"]; node["man_made"~"tower|chimney|mast"];
  way["power"="line"]; node["power"="tower"];
  way["bridge"];
);
out body; >; out skel qt;
```
JSON вместо XML — быстрее парсить. Набор фильтров зависит от уровня LOD: дальние тайлы запрашивают только крупные полигоны (вода, лес, ВПП, магистрали).

### 5.3. Кеширование
- Ключ кеша: `osm/{z}/{x}/{y}/{schemaVersion}`. Значение — сырой ответ (сжатый) **и/или** готовые бинарные буферы мешей **[РЕШЕНО, Q12: хранить оба; при смене версии генератора меши пересобираются из сырых данных без сетевого запроса]**.
- TTL сырых данных: 30 дней (OSM меняется, но для симулятора это неважно).
- LRU-вытеснение при превышении квоты (лимит, например, 1 ГБ; `navigator.storage.estimate()`).
- Очередь сетевых запросов с приоритетом по расстоянию/направлению полёта, ограничение параллелизма (Overpass: не более 2 одновременных), экспоненциальный backoff на 429/504.
- Префетч по вектору скорости: при 900 км/ч самолёт проходит тайл z14 за ~6–10 секунд — загрузка должна опережать на 2–3 тайла вперёд.

## 6. Здания: Simple 3D Buildings

Реализация по спецификации https://wiki.openstreetmap.org/wiki/Simple_3D_Buildings, эталон поведения — OSMBuildings.

### 6.1. Геометрия контура
- `way` с `building=*` и мультиполигоны с дырками (`outer`/`inner`, сборка колец из нескольких way).
- `building:part=*` — части здания. Если у здания есть части, контур `building` **не рисуется** (только части), согласно правилу S3DB: и при отношении `type=building` с ролями `outline`/`part` (части-линии и части-мультиполигоны), и без отношения — контур скрывается, если внутри него лежит хотя бы одна часть. Если у отношения нет частей, рисуется контур с тегами линии `outline` (теги отношения дополняют их).
- Триангуляция: earcut (для пола/плоской крыши), стены — квады по рёбрам кольца.
- Ориентация колец нормализуется (outer CCW, inner CW).

### 6.2. Высоты
Приоритет вычисления:
1. `height` (метры; парсинг единиц `m`, `ft`, `'`/`"`).
2. `building:levels` × 3 м (+ `roof:levels` × 3 м на крышу).
3. Значение по умолчанию по типу (`house`/`detached` ≈ 6 м, `garage` ≈ 3 м, `industrial` ≈ 8 м, прочие ≈ 9 м).

- `min_height` / `building:min_level` — низ части здания поднят над землёй.
- `roof:height` или `roof:levels`, иначе из `roof:angle`, иначе по умолчанию (≈ 3 м для скатных).
- Высота стены = `height − roof:height − min_height`.

### 6.3. Арки и проезды
- Арка/подворотня = `building:part` с `min_height > 0` над проездом, под которым нет других частей. Получается автоматически из корректного учёта `min_height` + отрисовки нижней грани («потолка») у части с `min_height > 0`.
- `building=roof` (навесы, АЗС) — только крыша и потолок, без стен; опоры не генерируются (в стиле эпохи допустимо).
- `building:part` с `min_height` и `height`, висящие в воздухе (переходы между корпусами) — так же.
- Тег `layer`, `location=underground`, `building=underground` — не рисуются.

### 6.4. Типы крыш (`roof:shape`)
Реализовано (`src/world/roof-shapes.ts`):
- `flat`, `skillion`, `gabled`, `half-hipped`, `hipped`, `side_hipped`, `side_half-hipped`, `gambrel`, `mansard`, `round`, `saltbox` (= `gabled_height_moved`), `bellcast_gable`, `crosspitched`, `sawtooth`, `butterfly` — кусочно-плоские поля высот;
- `pyramidal`, `cone` — веер от центроида к каждому ребру контура;
- `dome`, `onion` — тела вращения: контур масштабируется к центроиду по профилю (полусфера, луковица с выпуклостью ×1,22).
- Приближения: `hipped-and-gabled` → `half-hipped` (вертикальный щипец внутри контура не задаётся полем высот), `double_saltbox` → `saltbox`, `quadruple_saltbox` → `hipped`; `many` и неизвестные значения — `flat`.

Алгоритм:
- Ось конька — длинная сторона **минимального по площади ограничивающего прямоугольника** (вращающиеся калиперы по выпуклой оболочке); `roof:orientation=across` поворачивает на 90°; `roof:direction` (градусы или 16 румбов, `N`…`NNW`) задаёт сторону, куда смотрит главный скат, и ось конька перпендикулярно ему.
- Крыша — минимум/максимум нескольких плоскостей в рамке этого прямоугольника. Контур (с дырами) триангулируется earcut, каждый треугольник режется по линиям излома (где две плоскости сходятся на поверхности), так что каждая грань строго плоская; стены поднимаются до того же поля, поэтому фронтоны и торцы закрываются сами (оболочка замкнута — проверяется тестом для каждой формы).
- `skillion` без `roof:direction` — низкая сторона у первого ребра контура (правило OSM-4D).
- Высота крыши: `roof:height` → `roof:angle` (tg угла × полуширина, для `skillion` × полная глубина) → `roof:levels` × 3 м → умолчание формы: 30° для коньковых, 15° для `skillion`, полуширина для `dome`/`round`, 2,4 полуширины для `onion`, 2 — для `cone`.
- Без `height`: `building:levels` × 3 м + высота крыши (у плоской крыши `roof:levels` — ещё этажи). Длины принимают десятичную запятую (`3,7`).
- `building=roof` (навес) — без стен и без «потолка» у земли.

### 6.5. Цвет
- `building:colour` / `colour`, `roof:colour`: `#hex` и `rgb()` берутся **точно, как в теге** (Q43); CSS-имя приглушается (насыщенность ≤ 0,45, светлота 0,15–0,85, тон сохраняется), чтобы `red` стал красно-коричневым фасадом, а не плашкой.
- `building:material`, `roof:material` → цвет по таблице (кирпич, бетон, стекло, металл, черепица…).
- Без тегов — цвет по типу здания из ограниченного набора.

### 6.6. Что не входит
`building:facade`, окна, двери, `roof:ridge`/`roof:edge` как отдельные way'и (Roof lines), сложные формы `roof:shape=gabled` для L-образных контуров с несколькими коньками (во втором этапе через скелет).

## 7. Визуальный стиль

### 7.1. Палитра
- ~~[РЕШЕНО, Q4] Строгий индексный режим с LUT 6 бит на канал (VGA DAC).~~ Заменено **[РЕШЕНО, Q43]** (2026-11-15): ограничение VGA-палитрой снято, **разрешены любые цвета; текстуры запрещены**.
- Сцена рисуется сразу в RGB (RGBA8) нативного разрешения. Цвет грани — атрибут вершины `uint32`: либо произвольный RGB `0xRRGGBB` (цвет OSM-тега, материала, Landsat, модели самолёта — как есть, без подбора ближайшего цвета палитры), либо ссылка на рампу материала. Там же уровень ночной подсветки (3 бита) и флаг снега.
- Рампы материалов (трава, лес, вода, море, бетон, кирпич, асфальт, песок, снег, скалы, корпус, небо, HUD, самосвечение — 16 ступеней: 12 света + 4 тумана) остаются в LUT-текстуре: из неё же берутся небо, огни и цвета 2D-оверлея. LUT 8 бит на канал, без квантования 6 бит.
- Произвольный RGB освещается в шейдере по тому же ступенчатому закону, что и рампы (ступени 0–11 — свет от 40 % до 120 % цвета, 12–15 — туман к цвету горизонта), умноженному на свет времени суток и уровня подсветки. Поэтому характерный ступенчатый вид Flanker/F-117 сохраняется, меняется только набор цветов.
- Смешивания цветов в сцене нет; полупрозрачность (стекло, дым, облака) — только screen-door дизером по маске. Время суток, вспышки, ночь — подменой/интерполяцией LUT и параметров света.
- Палитра рельефа из Landsat (240 цветов) остаётся как собственный набор цветов рельефа — чтобы соседние тайлы сходились по цвету на швах, — но это уже не ограничение рендера.
- Дизеринг — нет (в эталонах его в 3D почти не было), опционально как режим.

### 7.2. Освещение и атмосфера
- Flat shading, одно направленное солнце + ambient. Нормали на грань.
- Туман по дистанции, **квантованный ступенями** (каждая ступень — следующий шаг к цвету горизонта).
- Небо — градиент полосами (5–10 полос) от зенита к горизонту; солнце — многоугольник.
- **[РЕШЕНО, Q45]** (2026-11-15) Горизонт не зависит от загрузки тайлов. Проход неба рисует ниже истинного горизонта «базовую землю» — ровную поверхность на той же кривой Земле, что и в шейдерах мира (опускание `d²/2R`), на высоте рельефа под камерой (по DEM, не ниже 0 м). Цвет — море (рампа моря, замерзает вместе с ней), если под камерой `h ≤ 0`, иначе приглушённый зелёно-оливковый цвет суши (со снегом зимой). Освещение — как у плоского рельефа, туман — те же ступени и дальности (15–55 км), поэтому вдали она уходит в дымку горизонта. Тайлы рисуются поверх, так что до загрузки и в дырах между тайлами видна земля до горизонта, а не небо.
- **[РЕШЕНО, Q16]** Погода в MVP: всегда ясно и штиль. Ветра, турбулентности и облаков нет. *(Облака — см. Q46.)*
- **[РЕШЕНО, Q44]** (2026-11-15) Солнечный день в хорошую погоду. «Солнечность» 0…1 берётся из общей облачности живой погоды (Open-Meteo `cloud_cover`): до 30 % — 1, от 90 % — 0, между ними линейно; погода неизвестна — считается ясной. URL `?clouds=80` задаёт облачность вручную (и на HUD). Солнечность смещает дневной ключевой кадр палитры от ровного «пасмурного» света к солнечному: небо глубже и синее, горизонт светлее, свет ярче (×1,12) и теплее, цвета освещённых поверхностей насыщеннее (×1,4 вокруг их яркости — и для произвольных RGB, и для рамп материалов; туман и небо не трогаются). Через закат эффект нарастает вместе с днём; ночь не меняется. ~~Облаков как геометрии по-прежнему нет.~~ Облака как геометрия — Q46.
- **[РЕШЕНО, Q46]** (2026-11-17) Облака как геометрия, из живой погоды. Open-Meteo дополнительно отдаёт облачность по ярусам (`cloud_cover_low/mid/high`) и точку росы `dew_point_2m`. Нижний ярус — на высоте `125 м × (T − Td)` над землёй (250–3000 м; без точки росы 1200 м), средний — на 3,5 км MSL или 2,5 км над землёй (выше нижнего); высокий ярус (перистые) не рисуется. Ярус меньше 5 % не рисуется; до 85 % — **кучевые из граней**: каждое облако — куча из нескольких искажённых икосаэдров, срезанных плоско по нижней границе, с тем же ступенчатым светом и туманом, что у мира (белые верхушки, серые днища); толщина растёт с облачностью, средний ярус площе. От 85 % — **сплошной слой**: бугристая гранёная крышка сверху («море облаков») и серый потолок снизу, до границы тумана. Облака стоят в собственной сетке тайлов 16 км (детерминированно по хешу, соседние тайлы сходятся) и дрейфуют с ветром на своей высоте. Внутри облака вид затягивается цветом облака **screen-door дизером** (Bayer 4×4, 8 ступеней плотности по глубине в облаке), без смешивания. URL `?clouds=80` — один нижний ярус с этой облачностью, `?clouds=80,900` — ещё и с нижней границей 900 м над землёй.

### 7.4. Модели
- Самолёт: low-poly 100–400 треугольников, плоские цвета, без текстур. Формат — собственный JSON: позиции и RGB-цвет на треугольник (`rgb`, `0xRRGGBB`); экспорт из `.blend` (`tools/export-aircraft.py`) берёт цвет из имени материала `<имя>_<RRGGBB>`.
  - Подвижные части, огни и модель разрушения задаются в `.blend`. Их строят перезапускаемые `tools/su27-rig.py` и `tools/f117-rig.py` на общем модуле `tools/aircraft_rig.py`; копии всех трёх лежат в файле модели как тексты. Неподвижный планёр остаётся в пределах 600 треугольников; рули, щитки и шасси идут сверх этого.
    - Шарниры Су-27: закрылки-элероны (флапероны), носки крыла, цельноповоротные стабилизаторы, рули направления, тормозной щиток.
    - Шарниры F-117: по два элевона на каждой половине W-образной задней кромки (тангаж и крен; внутренние ещё и опускаются как закрылки), две половины цельноповоротного V-образного оперения (тангаж и рыскание). Тормозного щитка на модели нет: переключатель только добавляет сопротивление.
    - У обоих: стойки и колёса шасси, створки ниш. Каждый шарнир — отдельный объект, который поворачивается вокруг своей локальной оси X. Угол считается как `clamp(su_bias + Σ коэффициент × сигнал, su_limits)` по свойствам объекта. Им же управляет драйвер Blender от пустышки `SU27_Controls` / `F117_Controls`: входы `pitch`, `roll`, `yaw`, `flaps`, `speedbrake`, `gear`, `nav`, `beacon`, `landing`; производные `gear_leg` и `gear_door` дают последовательность «створки → стойки → створки». Убранные стойки скрыты (`su_show`).
    - Огни: БАНО (красный слева, зелёный справа, белый на хвосте; у Су-27 на воздухозаборниках, у F-117 на законцовках крыла), два мигающих красных маяка, посадочная фара на передней стойке (горит только при выпущенном шасси).
    - Разрушение: булевы атрибуты граней корпуса `part_<id>` и свойство `su_part` у шарнирных объектов определяют, к какой отрывной части относится треугольник; пустышки `BREAK_<id>` задают законцовку части и нагрузку отрыва `max_load` (Н). Из них берутся `SU27.parts` и `F117.parts`.
    - Экспортёр прогоняет пустышку управления через набор значений и останавливается, если драйверы в файле считают иначе, чем игра (`src/flight/articulation.ts`). Модель без разметки получила бы части по прежним координатным правилам.
  - В игре положения задаёт `FlightModel.actuators`: команды ЭДСУ по тангажу, крену и рысканию, а также выпуск шасси (6 с на цикл), закрылков (4 с) и щитка (2 с). Это только отрисовка, физика по-прежнему берёт положения переключателей.
- Деревья **[РЕШЕНО, Q36]**: в MVP — конусы/пирамиды из 4–6 треугольников, инстансинг, ближняя зона ~2 км, по полигонам `landuse=forest`/`natural=wood`, детерминированный рассев по тайлу (сид от z/x/y).
  - Типы силуэтов: ель, лиственное, зонтичная (пиния) сосна, кипарис, пальма; ствол — коричневый, крона — цвет земли под деревом. Тип выбирается по «климатической широте» = |широта| + высота / 150 м (тропики → пальмы и лиственные, Средиземноморье → сосны, кипарисы, лиственные, умеренный пояс → лиственные и ели, север и горы → ели) и сужается тегом `leaf_type` (или старым `wood=coniferous/deciduous`).
- Прочие объекты: мачты, трубы, ЛЭП-опоры — процедурные призмы.

## 10. Производительность

| Метрика | Цель |
|---|---|
| FPS | 60 на ноутбуке с интегрированной графикой (Apple M1 / Intel Iris Xe) в нативном разрешении |
| Дальность видимости рельефа | 50–80 км (горизонт на высоте 5 км ≈ 250 км, но туман скрывает) |
| Дальность зданий | 3–6 км, с LOD: дальние — только призмы без крыш |
| Draw calls | < 500 за кадр (один меш на чанк × категорию) |
| Генерация тайла z14 в воркере | < 200 мс для плотного центра города |
| Время до первого кадра в новой точке | < 5 с при пустом кеше |

Приёмы: один буфер на чанк и категорию, цвет грани как атрибут вершины (`uint32`: RGB или рампа + флаги), никаких материалов и текстур, frustum culling по чанкам, отбрасывание мелких зданий по экранному размеру.

**[РЕШЕНО, Q47]** (2026-11-21) Кадр примерно вдвое быстрее без заметной разницы в картинке. Замер на Инсбруке с высоты 1500 м, 2880×1626, Apple M4 Pro: днём 11,4 → 5,5 мс, ночью 13,4 → 7 мс. Что сделано:
- **Reversed-Z вместо логарифмической глубины.** При наличии `EXT_clip_control` глубину пишут вершинные шейдеры: буфер `DEPTH_COMPONENT32F`, очистка в 0, `depthFunc(GREATER)`. Фрагментные шейдеры больше не пишут `gl_FragDepth`, поэтому на тайловых GPU снова работает ранний отсев скрытых пикселей. Без расширения (Safari) остаётся прежняя логарифмическая глубина через `gl_FragDepth`.
- **Варианты мирового шейдера.** Это один исходник, специализированный через `#define NO_WATER / NO_SPECKLE / NO_ROADS / NO_WINDOWS`:
  - `full` — вода и рельеф без точек;
  - `ground` — рельеф с точками, без дорог и окон;
  - `houses` — здания с окнами;
  - `bare` — облака и деревья.

  Каждый проход берёт вариант без ветвей, которые ему не нужны.
- **Точки на земле** (`worldDot`). Иерархия уровней разбирается группами по три уровня с развёрнутыми шагами. Спуск прекращается, как только выбранная подъячейка выходит за пределы досягаемости пикселя. Целочисленного деления в шейдере нет.
- **LOD зданий.** Двери, парапеты (и стенки у дымоходов) и надстройки на крыше записаны в буфер чанка после «ядра» (`coreVertexCount`), так что дальний чанк рисует только начало буфера:
  - деталь видна ближе 1500 м (`BUILDING_DETAIL_M`, по наклонной дальности до края чанка);
  - ночные дальние кольца рисуют только ядро.

  Схема OSM-меша — 53: в кеше пересобираются меши, сырые данные остаются.
- **Дальность мелких инстансов.** Кондиционеры видны ближе 1 км, фонари — ближе 1,5 км.

Не проверено: ракурсы плотной городской застройки, путь без `EXT_clip_control` и переходы точек при наборе высоты.

## 13. Приёмочные тесты (черновик)

- **[РЕШЕНО, Q20]** Автотесты — юнит-тесты генератора мешей (вход — OSM-фикстуры, выход — геометрия: число/площадь граней, высоты, ориентация колец, отсутствие NaN и вырожденных треугольников). Скриншот-регрессий нет; визуальная приёмка — ручной осмотр эталонных регионов.
- **[РЕШЕНО, Q8]** Эталонные регионы (снапшоты OSM фиксируются в репозитории как фикстуры для юнит-тестов и ручного осмотра):
  - **Фетхие, Мугла, Турция** — побережье с заливом и островами, горы до ~2000 м (Бабадаг) прямо над городом, плотная малоэтажная застройка на склонах, яхтенные марины. Ближайший аэропорт — Даламан (LTBS/DLM), ~45 км: маршрут взлёт в Даламане → пролёт над Фетхие → посадка.
  - **Инсбрук, Австрия** — аэропорт LOWI в узкой долине Инна, крутые склоны, здания на склонах (проверка посадки зданий на минимальную высоту рельефа).
- Разметка S3DB в обоих регионах, вероятно, бедная (в основном `building=*` без `roof:shape`), поэтому крыши и части проверяются ещё и на **синтетических фикстурах**: набор OSM-файлов с вручную размеченными зданиями на каждый тип крыши, мультиполигон с дырой, части с `min_height` (арка), `building=roof`, отношение `type=building`.
- Переход через антимеридиан (Берингов пролив) и смена тайлов на высоте 10 км без провалов.
- Полёт 15 минут на 900 км/ч без утечек памяти GPU (число буферов стабильно).
- Работа при недоступном Overpass: рельеф продолжает грузиться, OSM-слой деградирует без падения.

## 14. Правовое

- Код — **MIT** (Q11). Тайлы, собранные из OSM, — производная база данных под ODbL, распространяются с атрибуцией и той же лицензией.
- Данные OSM — ODbL: постоянная атрибуция «© OpenStreetMap contributors» на экране.
- Рельеф — атрибуция источников Terrain Tiles (SRTM, GMTED, ETOPO1 и др.).
- Соблюдение usage policy Overpass, OSM API и тайловых серверов; осмысленный User-Agent/Referer.
- Шрифт Unscii-16 — public domain (Q25).

## 15. Распространение и эксплуатация

- **[РЕШЕНО, Q26]** Репозиторий: `git init` сразу, публичный репозиторий на GitHub под MIT. Разработка сначала только локально (`vite dev`); публичная демка, PMTiles и (при необходимости) зеркало рельефа — на своём сервере, не на GitHub Pages и не на Cloudflare.
- **[РЕШЕНО, Q27]** В публичной демке: сбор ошибок JS/WebGL; отчёт о GPU/FPS — только по согласию; анонимная статистика посещений без cookies.
- **[РЕШЕНО, Q34]** Стек: self-hosted Umami или Plausible CE + собственный эндпоинт `/api/report` для ошибок и GPU/FPS, всё на своём сервере, без третьих сторон. Согласие — экран в канвасе при первом запуске.
- **[РЕШЕНО, Q33]** Конкретный сервер пока не выбран (до M6 неважно). Требования: nginx со статикой, Range-запросы для PMTiles, ~50–200 ГБ под тайлы. `pps-msk-b2` (продакшен) не подразумевается.

## 16. Архитектура кода

- **[РЕШЕНО, Q35]** В MVP — простые классы (`Aircraft`, `Camera`, …) с общим интерфейсом `update(dt)`; переход на ECS — когда появятся ракеты и цели.
- Внешний вид — оригинальный, вдохновлённый эстетикой эпохи; ассеты, названия и интерфейс конкретных игр не копируются.
