# ТЗ: OSM Flight Sim (рабочее название `sim-unlimited`)

> Статус: **v1.0, согласовано** 2026-11-08. Открытых пунктов нет; все решения (Q1–Q42) сведены в таблицу §12. Изменения после v1.0 — только через новую запись в §12.

## 1. Цель и рамка

Браузерный авиасимулятор, в котором мир — это реальная Земля, собранная на лету из данных OpenStreetMap и карты высот. Мир сквозной: можно взлететь в любой точке и лететь куда угодно без загрузочных экранов, тайлы подгружаются и выгружаются по мере полёта.

Визуальный язык — ранние 90-е: F-117A Nighthawk Stealth Fighter 2.0 (MicroProse), Su-27 Flanker (SSI). Плоская заливка полигонов без текстур, ограниченная VGA-палитра, дальний туман полосами, векторный HUD. При этом рендер в **нативном разрешении** экрана (без пикселизации, с учётом `devicePixelRatio`) — ретро-стиль достигается палитрой и геометрией, а не низким разрешением.

### 1.1. Не цели (для MVP)
- Фотореализм, текстуры, PBR, тени в реальном времени.
- Боевая часть, ИИ-противники, миссии. **[РЕШЕНО, Q1]** MVP — песочница (свободный полёт, взлёт/посадка где угодно); архитектура сущностей закладывается так, чтобы бой добавить позже без переделки.
- Мультиплеер.
- Сертифицируемая физика полёта.
- Мобильные устройства (только десктоп-браузер с WebGL2).

## 2. Платформа и стек

| Слой | Решение |

| Язык | TypeScript, сборка Vite |
| Фоновая обработка | Web Workers (парсинг OSM, триангуляция, генерация мешей), передача буферов через Transferable |

| Целевые браузеры | Chrome/Edge/Firefox/Safari последних двух версий, WebGL2 обязателен |

## 3. Система координат и сквозной мир

- **Тайловая сетка**: Web Mercator (slippy map, z/x/y), единая для рельефа и OSM-данных. Базовый уровень для зданий и дорог — z14 (~2.4 км по стороне на экваторе, ~1.4 км на широте Москвы).
- **Мировые координаты**: double-точность хранится на CPU (широта/долгота или ECEF); на GPU уходят float32 координаты **относительно плавающего начала (floating origin)**. При удалении самолёта от начала более чем на N км (предложено 5 км) происходит ребазирование: все загруженные чанки получают новый offset uniform'ом, без пересборки буферов.
- **Локальная плоскость**: каждый чанк строится в своей локальной ENU-системе (East-North-Up) от центра тайла, в метрах. Масштабные искажения Меркатора компенсируются при построении (переводим lat/lon → метры через ENU, а не через пиксели Меркатора).
- **Кривизна Земли** **[РЕШЕНО, Q12]**: мир плоский в пределах чанка; глобальная кривизна имитируется в вершинном шейдере опусканием на `d²/2R` от камеры. Даёт правильный горизонт на высоте без перехода на полноценный глобус.
- **Полюса**: Меркатор не покрывает >85°. Для MVP полёт ограничен ±85° широты.

## 4. Рельеф

### 4.1. Источник
**[РЕШЕНО, Q12]** AWS Terrain Tiles (формат Terrarium, PNG, `elevation = R*256 + G + B/256 − 32768`), публичный бакет с CORS, z0–z15. Альтернативы: Mapbox Terrain-RGB (нужен ключ), MapTiler (ключ), Copernicus GLO-30 через свой сервер.

### 4.2. Меш
- Квадродерево чанков (chunked LOD): уровень детализации зависит от расстояния до камеры и высоты полёта. Ближние чанки z13–z14, горизонт z8–z9.
- Сетка на чанк — регулярная, например 64×64 квадов; в ретро-стиле треугольники **намеренно крупные** и видимы как грани.
- Швы между уровнями: «юбки» (skirts) по краям чанка. Морфинг между LOD — опционально (в стиле эпохи допустим поп-ин, но лучше без мелькания).
- Освещение: flat shading (нормаль на грань), направленный «солнечный» свет, яркость квантуется в ступени палитры (см. §7).
- Окраска граней по высоте/уклону/landuse: вода, пляж, трава, лес, скалы, снег.
- Вода (океан): плоскость на 0 м под рельефом + полигоны `natural=water` из OSM.
- **[РЕШЕНО, Q13]** Граница суша/море — маска по DEM: `h ≤ 0` → вода. Известное и принятое ограничение: прибрежные низины ниже уровня моря (польдеры, дельты) затапливаются. Береговые water polygons OSM не используются.

### 4.3. Привязка объектов к рельефу
- Здание ставится на **минимальную** высоту рельефа под его контуром (фундамент уходит в склон, без висящих зданий).
- Дороги и полигоны землепользования «драпируются»: точки сэмплируются из той же карты высот, что и меш, плюс небольшой bias по глубине против z-fighting.
- ВПП выравниваются: рельеф под `aeroway=runway` сглаживается до плоскости (иначе взлёт невозможен на шумном DEM).
- **[РЕШЕНО, Q40]** Порядок загрузки: старт ждёт, пока в точке старта загрузятся и рельеф, и OSM (экран загрузки). Без данных не стартуем: если OSM недоступен — экран ожидания с повтором, без фолбэка. В полёте чанк рельефа сначала строится «как есть», а когда приходят данные OSM, ближние чанки z12–z14 перестраиваются в воркере с выровненными ВПП (короткий поп-ин допустим).

## 5. Данные OpenStreetMap

### 5.1. Источник для MVP **[РЕШЕНО, Q2]**
MVP — чисто статический фронт: прямые запросы к Overpass + кеш в IndexedDB. Все источники скрыты за интерфейсом `TileSource` (`fetch(z,x,y,lod) → нормализованные фичи`), чтобы позже подключить свои векторные тайлы (PMTiles) или прокси без изменений в генераторе мешей.

- **[РЕШЕНО, Q42]** Прямой запрос из браузера невозможен: главный инстанс Overpass отдаёт 406 браузерным User-Agent, а `fetch` не позволяет переопределить UA. В dev-режиме запросы идут через same-origin прокси Vite (`/overpass`), который подставляет описательный UA. Статический прод-билд до M6 к Overpass обращаться не может — публичный путь только через свои тайлы (Q9, M6).

- **Overpass API** с фильтрами по bbox тайла z14. Политика использования главного инстанса: порядка 10 000 запросов/сутки и ~1 ГБ трафика на пользователя; для пет-проекта/демо подходит, для публичного запуска — нет.
- **OSM API 0.6 `/map`** — не подходит как основной источник: лимит 0.25°² и 50 000 нод, политика запрещает массовую загрузку для рендера. Допустим как отладочный fallback.
- **[РЕШЕНО, Q9]** Проект будет публичной демкой, а публичный Overpass её трафик не выдержит и политика это запрещает. Поэтому перед публичным запуском обязателен этап M6: свои векторные тайлы (собственная генерация из planet/extract через tilemaker/planetiler в формате MVT/PMTiles).

### 5.2. Запрос Overpass (черновик)
```
[out:json][timeout:25][bbox:{s},{w},{n},{e}];
(
  way["building"]; relation["building"]["type"="multipolygon"];
  way["building:part"]; relation["building:part"]["type"="multipolygon"];
  relation["type"="building"];
  way["highway"~"motorway|trunk|primary|secondary|tertiary|residential|unclassified"];
  way["railway"="rail"];
  way["aeroway"~"runway|taxiway|apron|helipad"]; node["aeroway"="helipad"];
  way["natural"~"water|wood|scrub|beach|bare_rock"]; relation["natural"="water"];
  way["waterway"~"river|riverbank|canal"];
  way["landuse"]; relation["landuse"];
  way["leisure"~"park|pitch|golf_course"];
  way["man_made"~"bridge|tower|chimney|mast"]; node["man_made"~"tower|chimney|mast"];
  way["power"="line"]; node["power"="tower"];
  way["bridge"];
);
out body; >; out skel qt;
```
JSON вместо XML — быстрее парсить. Набор фильтров зависит от уровня LOD: дальние тайлы запрашивают только крупные полигоны (вода, лес, ВПП, магистрали).

### 5.3. Кеширование
- Ключ кеша: `osm/{z}/{x}/{y}/{schemaVersion}`. Значение — сырой ответ (сжатый) **и/или** готовые бинарные буферы мешей **[РЕШЕНО, Q12: хранить оба; при смене версии генератора меши пересобираются из сырых данных без сетевого запроса]**.
- TTL сырых данных: 30 дней (OSM меняется, но для симулятора это неважно).
- LRU-вытеснение при превышении квоты (лимит, например, 1 ГБ; `navigator.storage.estimate()`).
- Очередь сетевых запросов с приоритетом по расстоянию/направлению полёта, ограничение параллелизма (Overpass: не более 2 одновременных), экспоненциальный backoff на 429/504.
- Префетч по вектору скорости: при 900 км/ч самолёт проходит тайл z14 за ~6–10 секунд — загрузка должна опережать на 2–3 тайла вперёд.

## 6. Здания: Simple 3D Buildings

Реализация по спецификации https://wiki.openstreetmap.org/wiki/Simple_3D_Buildings, эталон поведения — OSMBuildings.

### 6.1. Геометрия контура
- `way` с `building=*` и мультиполигоны с дырками (`outer`/`inner`, сборка колец из нескольких way).
- `building:part=*` — части здания. Если у здания есть части, контур `building` **не рисуется** (только части), согласно правилу S3DB; отношение `type=building` с ролями `outline`/`part` поддерживается.
- Триангуляция: earcut (для пола/плоской крыши), стены — квады по рёбрам кольца.
- Ориентация колец нормализуется (outer CCW, inner CW).

### 6.2. Высоты
Приоритет вычисления:
1. `height` (метры; парсинг единиц `m`, `ft`, `'`/`"`).
2. `building:levels` × 3 м (+ `roof:levels` × 3 м на крышу).
3. Значение по умолчанию по типу (`house`/`detached` ≈ 6 м, `garage` ≈ 3 м, `industrial` ≈ 8 м, прочие ≈ 9 м).

- `min_height` / `building:min_level` — низ части здания поднят над землёй.
- `roof:height` или `roof:levels`, иначе из `roof:angle`, иначе по умолчанию (≈ 3 м для скатных).
- Высота стены = `height − roof:height − min_height`.

### 6.3. Арки и проезды
- Арка/подворотня = `building:part` с `min_height > 0` над проездом, под которым нет других частей. Получается автоматически из корректного учёта `min_height` + отрисовки нижней грани («потолка») у части с `min_height > 0`.
- `building=roof` (навесы, АЗС) — только крыша и потолок, без стен; опоры не генерируются (в стиле эпохи допустимо).
- `building:part` с `min_height` и `height`, висящие в воздухе (переходы между корпусами) — так же.
- Тег `layer`, `location=underground`, `building=underground` — не рисуются.

### 6.4. Типы крыш (`roof:shape`)
MVP (обязательно):
- `flat`
- `skillion` (с `roof:direction`)
- `gabled` (направление конька — по длинной оси минимального ограничивающего прямоугольника; `roof:orientation=across` поворачивает; `roof:direction`)
- `hipped`
- `pyramidal`
- `dome`
- `half-hipped`

Второй этап:
- `gambrel`, `mansard`, `round`, `onion`, `saltbox`, `cone`, `side_hipped`.

Алгоритм:
- Простые формы (`pyramidal`, `dome`, `onion`, `cone`) — от центроида, работают на любом выпуклом/почти выпуклом контуре.
- `gabled`/`skillion`/`half-hipped`/`gambrel`/`saltbox` — через проекцию на ось конька (точная для 4-угольников; для сложных контуров — эвристика как в OSMBuildings).
- `hipped`/`mansard` на произвольных многоугольниках — через **прямой скелет (straight skeleton)** **[РЕШЕНО, Q12: своя реализация или порт; если скелет не строится — фолбэк на `flat`]**.
- Сложные/вырожденные контуры (>N вершин, самопересечения) — фолбэк на `flat`, с логированием.

### 6.5. Цвет
- `building:colour` / `colour`, `roof:colour` (CSS-имена и `#hex`) → **квантуются в ближайший цвет палитры**.
- `building:material`, `roof:material` → цвет по таблице (кирпич, бетон, стекло, металл, черепица…).
- Без тегов — цвет по типу здания из ограниченного набора.

### 6.6. Что не входит
`building:facade`, окна, двери, `roof:ridge`/`roof:edge` как отдельные way'и (Roof lines), сложные формы `roof:shape=gabled` для L-образных контуров с несколькими коньками (во втором этапе через скелет).

## 7. Визуальный стиль

### 7.1. Палитра
- **[РЕШЕНО, Q4]** Строгий индексный режим: сцена рисуется в R8UI/R8-буфер индексов нативного разрешения, цвет появляется только в финальном проходе через LUT-текстуру 256×1 (RGB 6 бит на канал, как у VGA DAC). Освещение и туман — сдвиг индекса внутри рампы. Смешивания цветов нет; полупрозрачность (стекло, дым, облака) — только screen-door дизером по маске. Время суток, вспышки, ночь — подменой/интерполяцией палитры (palette cycling).
- Предложение: палитра из ~16 рамп по 8–16 ступеней (трава, лес, вода, бетон, кирпич, асфальт, песок, снег, небо, корпус самолёта…). Освещение = выбор ступени в рампе, а не умножение цвета. Это даёт характерный ступенчатый вид Flanker/F-117.
- Дизеринг — нет (в эталонах его в 3D почти не было), опционально как режим.

### 7.2. Освещение и атмосфера
- Flat shading, одно направленное солнце + ambient. Нормали на грань.
- Туман по дистанции, **квантованный ступенями** (каждая ступень — следующий индекс рампы к цвету горизонта).
- Небо — градиент полосами (5–10 полос) от зенита к горизонту; солнце — многоугольник.
- **[РЕШЕНО, Q16]** Погода в MVP: всегда ясно и штиль. Ветра, турбулентности и облаков нет.
- **[РЕШЕНО, Q17]** Время суток при старте — реальное для точки и текущего момента (положение солнца по дате/координатам), с ручной подстройкой и ускорением времени.
- **[РЕШЕНО, Q7]** Время суток в MVP: день/закат/ночь — набором палитр с интерполяцией по положению солнца. Огни в MVP — только ВПП и рулёжки (кромочные, торцевые, осевые; генерируются из `aeroway=runway`/`taxiway` + `width`, `length`), рисуются точками фиксированного экранного размера с индексом «самосвечения», который не затемняется ночной палитрой. Огни улиц и окон — после MVP.

### 7.3. Рендер-конвейер
1. Рендер сцены в offscreen-буфер нативного разрешения (`canvas.width = clientWidth * devicePixelRatio`).
2. MSAA — **[РЕШЕНО, Q12: выключен по умолчанию]** (лесенки рёбер — часть стиля), переключатель в настройках.
3. Пост-проход: индексный буфер → RGB через LUT палитры (всегда, Q4), HUD поверх.
4. HUD — векторные линии (тонкие, яркие, зелёный/жёлтый), шрифт — растровый 8×16, масштабируемый целым множителем. **[РЕШЕНО, Q25]** Шрифт — как в нашем веб-порте F19 (`~/dev/pets/f19decomp/web`): Unscii-16 (public domain, исходник `unscii-16.hex`, есть кириллица). Шрифты, извлечённые из оригинальных EXE MicroProse, не используются.

### 7.4. Модели
- Самолёт: low-poly 100–400 треугольников, плоские цвета, без текстур. Формат — glTF без материалов (только vertex colors / индекс палитры) или собственный JSON.
- Деревья **[РЕШЕНО, Q36]**: в MVP — конусы/пирамиды из 4–6 треугольников, инстансинг, ближняя зона ~2 км, по полигонам `landuse=forest`/`natural=wood`, детерминированный рассев по тайлу (сид от z/x/y).
- Прочие объекты: мачты, трубы, ЛЭП-опоры — процедурные призмы.

## 8. Полётная модель

- **[РЕШЕНО, Q5]** Упрощённая 6DOF (уровень «Flanker-лайт»), без моделирования систем самолёта.
- 6DOF твёрдое тело, интегрирование с фиксированным шагом 120 Гц; аэродинамика через табличные `CL(α)`, `CD(α)`, `Cm`, демпфирование по угловым скоростям; тяга с форсажем; сваливание; шасси, закрылки, тормоз, тормозные щитки.
- **[РЕШЕНО, Q6]** Два самолёта в MVP: Су-27 (манёвренный, тяговооружённость > 1) и F-117A (дозвуковой, вялый по крену, плохие несущие свойства граней). Оба — собственные low-poly модели с нуля по общедоступным чертежам/ТТХ, ~200–400 треугольников. Различие поведения задаётся только JSON-описанием (массы, моменты инерции, площадь крыла, таблицы коэффициентов, тяга, шасси) — это проверка, что модель действительно параметризуется.
- Атмосфера ISA (плотность от высоты).
- Столкновения: с рельефом (сэмпл высоты), со зданиями (AABB/призма по контуру в ближней зоне), с водой. Посадка — проверка вертикальной скорости и крена.

### 8.1. Звук **[РЕШЕНО, Q15]**
Web Audio, процедурный синтез без сэмплов: двигатель (громкость/тон от тяги, форсаж), ветер от скорости, шасси, касание полосы, сигнал сваливания.

## 9. Управление и камеры

- Ввод: клавиатура (обязательно), мышь как джойстик, Gamepad API, джойстик через Gamepad API.
- **[РЕШЕНО, Q37]** Своя раскладка по умолчанию (стрелки — ручка, `A`/`Z` или `+`/`−` — тяга, `G` — шасси, `F` — закрылки, `B` — тормоза, F1–F8 — камеры); переназначение клавиш — в MVP; мышь как джойстик включается в настройках.
- **[РЕШЕНО, Q14]** Вид из кабины — только HUD поверх вида, без рамы фонаря и приборки. Символика HUD у самолётов разная (Су-27 и F-117A — каждый своя).
- **[РЕШЕНО, Q21]** Единицы на HUD общие для обоих самолётов и выбираются в настройках (метрика/империал); различается только символика.
- **[РЕШЕНО, Q23]** Крушение (столкновение или жёсткая посадка): вспышка палитрой, камера облетает место крушения, затем меню «рестарт / новая точка». Частичных повреждений в MVP нет — исход «ок» или «разбился».
- **[РЕШЕНО, Q24]** Весь UI (стартовый экран, выбор самолёта и точки, настройки, пауза, крушение) рисуется в том же WebGL-канвасе растровым шрифтом (Q25); DOM-интерфейса нет.
- **[РЕШЕНО, Q31]** Языки интерфейса: английский, русский, украинский — словарь строк с первого дня.
- **[РЕШЕНО, Q38]** В Unscii-16 нет Ґ ґ Є є (U+0490, U+0491, U+0404, U+0454): рисуем 4 глифа 8×16 сами на основе Г/г и Е/е и храним патчем к hex-файлу в репозитории. `unscii-16-full` (GPL) не используется.
- **[РЕШЕНО, Q39]** Язык при первом запуске — по `navigator.language` (uk → UA, ru → RU, иначе EN), выбор запоминается. Надписи HUD — на «родном» языке самолёта (Су-27 — русский, F-117A — английский) независимо от языка интерфейса.
- **[РЕШЕНО, Q28]** Во внешних камерах — минимальная строка: скорость, высота, курс.
- **[РЕШЕНО, Q30]** Доступность не закладывается: UI в канвасе, без поддержки скринридеров и масштаба браузера.
- Камеры (классический набор эпохи): кабина с HUD, внешняя с орбитой, погоня, «пролёт» (flyby — камера ставится впереди по курсу), вышка (с ближайшего аэродрома), вид на цель/объект.
- Интерфейс: выбор точки старта — поиск по аэропортам **[РЕШЕНО, Q19: каталог из OSM `aeroway=aerodrome`]** и по координатам; старт на ВПП или в воздухе. **[РЕШЕНО, Q29]** Текстового ввода координат нет: произвольная точка задаётся через URL (Q18) или выбором на мини-карте в канвасе. **[РЕШЕНО, Q32]** Мини-карта строится только из своих данных: Terrarium z3–z8 в палитре, береговая линия по маске DEM, точки аэродромов; сторонних растровых тайлов нет. Та же карта показывается в паузе. **[РЕШЕНО, Q22]** До M6 — фиксированный список эталонных аэродромов (LTBS, LOWI) + произвольная точка; глобальный индекс аэродромов (выгрузка `aeroway=aerodrome` из OSM в статический JSON) — в M6.
- **[РЕШЕНО, Q41]** Старт в воздухе: 1500 м над рельефом, 70% максимальной крейсерской скорости самолёта, курс из URL или на север. Ускорение времени ×1/×10/×60/×600 действует только на солнце и палитры; физика всегда в реальном времени.
- **[РЕШЕНО, Q18]** Состояние в URL: `#lat,lon,alt,hdg,aircraft,time` открывает тот же момент полёта (ссылка для шаринга). Пауза — в MVP. Реплей — после MVP (ввод пишется с фиксированным шагом 120 Гц, чтобы его можно было добавить).

## 10. Производительность

| Метрика | Цель |
|---|---|
| FPS | 60 на ноутбуке с интегрированной графикой (Apple M1 / Intel Iris Xe) в нативном разрешении |
| Дальность видимости рельефа | 50–80 км (горизонт на высоте 5 км ≈ 250 км, но туман скрывает) |
| Дальность зданий | 3–6 км, с LOD: дальние — только призмы без крыш |
| Draw calls | < 500 за кадр (один меш на чанк × категорию) |
| Генерация тайла z14 в воркере | < 200 мс для плотного центра города |
| Время до первого кадра в новой точке | < 5 с при пустом кеше |

Приёмы: один буфер на чанк и категорию, индексы палитры как атрибут вершины (1 байт), никаких материалов, frustum culling по чанкам, отбрасывание мелких зданий по экранному размеру.

## 13. Приёмочные тесты (черновик)

- **[РЕШЕНО, Q20]** Автотесты — юнит-тесты генератора мешей (вход — OSM-фикстуры, выход — геометрия: число/площадь граней, высоты, ориентация колец, отсутствие NaN и вырожденных треугольников). Скриншот-регрессий нет; визуальная приёмка — ручной осмотр эталонных регионов.
- **[РЕШЕНО, Q8]** Эталонные регионы (снапшоты OSM фиксируются в репозитории как фикстуры для юнит-тестов и ручного осмотра):
  - **Фетхие, Мугла, Турция** — побережье с заливом и островами, горы до ~2000 м (Бабадаг) прямо над городом, плотная малоэтажная застройка на склонах, яхтенные марины. Ближайший аэропорт — Даламан (LTBS/DLM), ~45 км: маршрут взлёт в Даламане → пролёт над Фетхие → посадка.
  - **Инсбрук, Австрия** — аэропорт LOWI в узкой долине Инна, крутые склоны, здания на склонах (проверка посадки зданий на минимальную высоту рельефа).
- Разметка S3DB в обоих регионах, вероятно, бедная (в основном `building=*` без `roof:shape`), поэтому крыши и части проверяются ещё и на **синтетических фикстурах**: набор OSM-файлов с вручную размеченными зданиями на каждый тип крыши, мультиполигон с дырой, части с `min_height` (арка), `building=roof`, отношение `type=building`.
- Переход через антимеридиан (Берингов пролив) и смена тайлов на высоте 10 км без провалов.
- Полёт 15 минут на 900 км/ч без утечек памяти GPU (число буферов стабильно).
- Работа при недоступном Overpass: рельеф продолжает грузиться, OSM-слой деградирует без падения.

## 14. Правовое

- Код — **MIT** (Q11). Тайлы, собранные из OSM, — производная база данных под ODbL, распространяются с атрибуцией и той же лицензией.
- Данные OSM — ODbL: постоянная атрибуция «© OpenStreetMap contributors» на экране.
- Рельеф — атрибуция источников Terrain Tiles (SRTM, GMTED, ETOPO1 и др.).
- Соблюдение usage policy Overpass, OSM API и тайловых серверов; осмысленный User-Agent/Referer.
- Шрифт Unscii-16 — public domain (Q25).

## 15. Распространение и эксплуатация

- **[РЕШЕНО, Q26]** Репозиторий: `git init` сразу, публичный репозиторий на GitHub под MIT. Разработка сначала только локально (`vite dev`); публичная демка, PMTiles и (при необходимости) зеркало рельефа — на своём сервере, не на GitHub Pages и не на Cloudflare.
- **[РЕШЕНО, Q27]** В публичной демке: сбор ошибок JS/WebGL; отчёт о GPU/FPS — только по согласию; анонимная статистика посещений без cookies.
- **[РЕШЕНО, Q34]** Стек: self-hosted Umami или Plausible CE + собственный эндпоинт `/api/report` для ошибок и GPU/FPS, всё на своём сервере, без третьих сторон. Согласие — экран в канвасе при первом запуске.
- **[РЕШЕНО, Q33]** Конкретный сервер пока не выбран (до M6 неважно). Требования: nginx со статикой, Range-запросы для PMTiles, ~50–200 ГБ под тайлы. `pps-msk-b2` (продакшен) не подразумевается.

## 16. Архитектура кода

- **[РЕШЕНО, Q35]** В MVP — простые классы (`Aircraft`, `Camera`, …) с общим интерфейсом `update(dt)`; переход на ECS — когда появятся ракеты и цели.
- Внешний вид — оригинальный, вдохновлённый эстетикой эпохи; ассеты, названия и интерфейс конкретных игр не копируются.
